    Windows Forms

    Es un «conjunto de clases que permite desarrollar aplicaciones basadas en Windows». Es orientado a eventos, y la mayoría de los controles está en System.Windows.Forms (Presentación de la Unidad 3, diapositivas 3 y 8).

    Todas las diapositivas de esta sección son de esa presentación.

    Según la diapositiva 3, incluye interfaz de usuario rica, acceso al framework de .NET, ejecución en un entorno manejado, seguridad integrada, diseño orientado a objetos, orientación a eventos, aplicaciones orientadas a datos con ADO.NET, fácil acceso a servicios web y elección de lenguaje.

    .NET tiene tres componentes para aplicaciones de escritorio (diapositiva 4).

    • Windows Forms: componentes para gestionar ventanas y controles.
    • GDI+: las funciones que encapsulan las funcionalidades gráficas de bajo nivel. Es el sistema gráfico 2D de Microsoft y Windows Forms lo aprovecha al 100%. Trae dibujo (System.Drawing), lápices, pinceles e imágenes, alpha blending, degradés de color e imágenes en varios formatos además de Bitmap (diapositiva 13).
    • Windows Presentation Foundation: la segunda generación de aplicaciones de escritorio.

    Crear una aplicación Windows Forms «es tan fácil como instanciar y extender los formularios de Windows». El proceso tiene estos pasos (diapositiva 7).

    1. Crear un proyecto nuevo con la estructura de una aplicación Windows Forms.
    2. Definir los formularios necesarios.
    3. Con el diseñador, agregarles controles según el propósito y configurar los manejadores de eventos.
    4. Agregar tu código para el comportamiento y la apariencia.
    5. Diseñar tus propios controles.

    Cómo arranca una aplicación

    Al crear el proyecto se crea un formulario principal. La aplicación arranca con la línea Application.Run(new Form1()), que «no es un setting mágico del proyecto» (diapositiva 15).

    Hay dos tipos de aplicación (diapositiva 17).

    • SDI (single document interface): un solo formulario activado.
    • MDI (multiple document interface): un formulario padre y muchos hijos. En el padre se setea la propiedad IsMDIContainer, y en los hijos, IsMDIChild en true.

    InitializeComponent

    Es un método agregado por Visual Studio. Tiene «toda la creación de los controles sobre la superficie de diseño, el posicionamiento, etc.». Es código generado y se mantiene sincronizado (diapositiva 16).

    El diseñador genera ese código, y «Partial Class permite separar la implementación de una clase en varios archivos fuente» (diapositiva 32).

    • Si se cierra desde la cruz, la respuesta por defecto es DialogResult.Cancel.
    • La propiedad AcceptButton del formulario elige el botón por defecto. Apretar Enter es como hacer clic en ese botón.

    ClickOnce

    ¿Qué tecnología permite que una aplicación windows se actualice sola, con mínima interacción?1° parcial 01/06/2024 y 2° parcial 14/09/2026

    ClickOnce «permite actualizaciones automáticas de aplicaciones Windows que pueden ser instaladas con mínima interacción del usuario». Fuente: Presentación de la Unidad 3, diapositiva 54.

    Supera tres obstáculos propios de la distribución de software (diapositiva 54).

    • Las dificultades para actualizar las aplicaciones.
    • El impacto en el equipo del usuario.
    • Los permisos.

    «Cualquier aplicación Windows Form o modo Consola» se publica con ClickOnce. Se publica de tres modos: como página web, desde una dirección de red local o desde un dispositivo de almacenamiento. Las aplicaciones ClickOnce pueden verificar si hay versiones nuevas y reemplazar solas los componentes actualizados (diapositiva 55).

    ADO.NET

    ADO.NET es «un conjunto de clases para conectar y manipular fuentes de datos» (Presentación de la Unidad 4, Capítulo 1, diapositiva 3). Todas las diapositivas de esta sección son de esa presentación.

    ¿Para qué puede usarse ADO.NET?2° parcial 14/09/2026

    «Diseñado para trabajar con cualquier origen de datos (no solo base de datos relacionales)». Sus modelos muestran fuentes OLEDB, como Access y Excel. El laboratorio de la Unidad 4 trabaja además con archivos TXT y XML. Fuente: Presentación de la Unidad 4, Capítulo 1, diapositivas 3, 4 y 44.

    Sus características, según la diapositiva 3:

    • Diseñado para trabajar en entornos desconectados.
    • Modelo de programación con soporte para XML.
    • Brinda clases, estructuras, interfaces y enumeraciones para administrar el acceso a datos.
    • Basado en Data Providers.
    • Diseñado para trabajar con cualquier origen de datos, no solo bases relacionales.

    Los namespaces se importan con using. Por un lado, System.Data y System.Data.Common. Por otro, el que depende del proveedor que uses, que puede ser System.Data.SqlClient, System.Data.OleDB, System.Data.ODBC o System.Data.OracleClient (diapositiva 6).

    Los objetos cambian de nombre según el proveedor: SqlConnection, OleDbConnection, OdbcConnection, OracleConnection (diapositiva 21). Se trabaja de dos maneras (diapositivas 4 y 5).

    • Con DataSets: el DataAdapter llena tablas en memoria.
    • Con objetos: el DataReader lee y vos armás tus objetos.

    Connection

    Establece la comunicación física entre la aplicación y la base. Propiedad ConnectionString. Métodos Open, Close y BeginTransaction (diapositivas 20 y 22). Representa una conexión al Data Source, y permite personalizarla e iniciar, confirmar y abortar transacciones (diapositiva 20). Las clases xxxConnection heredan de System.Data.Common.DbConnection (diapositiva 22).

    Crear la conexión

    string sCnn = "data source=localhost; " +
    "initial catalog=northwind; integrated security=true";
SqlConnection conn = new SqlConnection(sCnn);

    Presentación de la Unidad 4, Capítulo 1, diapositiva 21

    La cadena de conexión puede tener datos sensibles. Va en el archivo de configuración, en <connectionStrings>. Se lee con ConfigurationManager.ConnectionStrings["..."].ConnectionString (diapositiva 23). Sus parámetros son Data Source, Initial Catalog, Integrated Security, Connection Timeout, User ID, Password y Provider (diapositiva 24).

    Command

    «Representa una Instrucción SQL o un procedimiento almacenado que se ejecuta en un origen de datos.» Requiere un objeto Connection y soporta parámetros (diapositiva 26). Es específico de cada proveedor (SQLCommand, ODBCCommand, OLEDBCommand, OracleCommand), se puede usar solo o a través de DataAdapters, y «expone 4 métodos importantes para devolver datos» (diapositiva 26).

    PropiedadesMétodos
    CommandType, CommandText, Connection, ParametersExecuteReader(), ExecuteScalar(), ExecuteNonQuery(), ExecuteXMLReader()

    Fuente: diapositiva 27. Los laboratorios los usan así.

    • ExecuteReader «crea un objeto DataReader que nos permite leer los datos» (Unidad 4, Capítulo 1, Laboratorio 3, pág. 6).
    • ExecuteNonQuery ejecuta los comandos de insertar, modificar y eliminar (mismo laboratorio, págs. 8 y 9).

    DataReader

    Es de solo avance y solo lectura (forward-only, read-only). Da acceso rápido, usa pocos recursos y queda conectado al origen. La conexión la manejás vos. Los datos se manejan por código o con controles enlazados (diapositiva 32).

    DataTable y DataSet

    ObjetoQué es
    DataTableObjeto central si no usás objetos. «Desconoce su origen de datos, por lo que funciona como una entidad independiente» (diapositiva 7)
    DataSet«Representación de datos en memoria». Una colección de DataTable, con integridad por DataRelation. Desconoce el origen (diapositiva 13)
    DataSet tipadoClase generada en diseño que hereda de DataSet. Da completado de sentencias y comprobación de tipos en compilación (diapositiva 17)

    Del DataTable la diapositiva 7 agrega tres cosas. Su esquema lo define DataColumnCollection. Mantiene la integridad de los datos con Constraints. Y con sus eventos se controlan los distintos estados de los registros. Está formado por DataRow y DataColumn (diapositiva 8).

    Fuente: diapositivas 9 y 10. DataSet.Load y DataTable.Load cargan desde un DataReader, como OLEDbDataReader o SqlDataReader, y dan un control más específico de los datos (diapositiva 14).

    DataAdapter

    «Gestiona el intercambio de datos entre DataTables y un Data Source», con .Fill y .Update. Tiene SelectCommand, InsertCommand, UpdateCommand y DeleteCommand (diapositivas 35 y 37). También provee relaciones entre tablas y columnas, y el usuario puede saltarse los comandos Insert, Update y Delete (diapositiva 35). El dibujo de la diapositiva 37 suma TableMappings entre sus piezas.

    En criollo

    El DataReader es como leer un libro de corrido con el bibliotecario al lado. Es rápido, pero sin volver atrás y con la biblioteca abierta para vos. El DataAdapter te saca una copia a tu casa. La trabajás sin conexión, en un DataSet, y después llevás los cambios.

    DataBinding y transacciones

    DataBinding enlaza objetos con datos y controles WinForms, sin escribir código, y se establece en diseño (diapositiva 39). TransactionScope agrupa operaciones en una unidad lógica de trabajo, con el método .Complete y dentro de un using (diapositiva 42).

    • El DataBinding automatiza operaciones y permite navegar y editar registros. Admite varios orígenes, como un DataSet, un servicio web o una base de datos (diapositiva 39).
    • El TransactionScope controla y conserva la coherencia e integridad de todas las acciones, y puede contener transacciones locales o distribuidas. Pide agregar la referencia a System.Transaction, y la clase está en ese namespace (diapositiva 42).

    Entity Framework

    Todas las diapositivas de esta sección son de la Presentación de la Unidad 4, Capítulo 2.

    Trabajar con ADO.NET obliga a manejar dos mundos, objetos y datos relacionales, con dos lenguajes y una API que los une (diapositivas 3 y 4). Entity Framework resuelve eso: «En lugar de operar sobre filas y columnas se opera sobre objetos denominados entities». Tiene soporte para LINQ. La cátedra cubre solo Code First (diapositiva 5).

    La presentación se titula «ORM Entity Framework» (diapositiva 1). El laboratorio lo presenta como el ORM con el que se aprenden «los fundamentos de los ORM (Object Relational Mapping)», para manipular los datos del dominio modelados como clases y objetos (Unidad 4, Capítulo 2, Laboratorio, pág. 1).

    El problema que resuelve, con más detalle (diapositivas 3 y 4):

    • Armar el puente entre el modelo de objetos y el relacional con DataSets o DataReaders «genera un costo elevado en terminos de esfuerzo de desarrollo».
    • Hay que conocer dos lenguajes, C# y SQL, con sintaxis, tipos de datos, herramientas y paradigmas distintos.
    • Además hay que aprender la API que une los dos mundos, ADO.NET. Es «potente, pero frágil y consumidor importante de tiempo».

    EF apareció con el Service Pack 1 de .NET 3.5, en System.Data.Entity.dll. Soporta dos formas de modelar las entidades, Code First y el EF Designer. La cátedra cubre solo Code First porque el Designer «presenta varios problemas y ya no esta incluido en .NET Core» (diapositiva 5). El contenido de la presentación nombra también las Conventions como forma de mapeo, sin desarrollarlas (diapositiva 2).

    Qué es válido decir sobre EF2° parcial 14/09/2026

    Pregunta de selección múltiple. Mezcla frases verdaderas sobre EF con la definición de otras tecnologías. Para distinguirlas, repasá esta sección, LINQ y qué dice la presentación de cada cosa.

    DbContext y DbSet

    DbContext tiene el constructor que toma la cadena de conexión, Entry, SaveChanges y SaveChangesAsync, y Database. «Representa una combinación de los patrones Unit of Work y Repository» (diapositiva 7).

    Miembro de DbContextQué hace
    DbContextConstructor. Toma de parámetro la cadena de conexión a la base
    Entry, Entry<TEntity>Obtiene el DbEntityEntry de una entidad, con información sobre ella y la posibilidad de hacer acciones sobre ella
    SaveChanges, SaveChangesAsyncGraba en la base los cambios del context actual y devuelve el número de entidades afectadas
    DatabaseAcceso a la base. Creación, eliminación, validación de existencia, ejecución de procedimientos almacenados, sentencias SQL y funciones transaccionales

    Fuente: diapositiva 7. La misma diapositiva completa la frase de los patrones. Unit of Work y Repository «pueden ser usados para consultar datos y acumular cambios sobre los objetos que luego puedan ser guardados en un solo Unit of Work».

    Mapeo

    Se configura con Data Annotations (diapositiva 11) o con Fluent API, en OnModelCreating (diapositiva 12). Las annotations «se utilizan para configurar las entidades y mapear tablas y columnas» (diapositiva 11).

    Lo mismo con Fluent API

    internal class MyContext : DbContext
{
    public DbSet<Blog> Blogs { get; set; }

    Blazor

    Es un framework de Microsoft, de código abierto, para desarrollar «aplicaciones web de una sola página (SPA) dinámicas y eficientes usando C# y Razor» (Presentación de la Unidad 5, Blazor, diapositiva 3). Todas las diapositivas de esta sección son de esa presentación.

    Blazor ServerBlazor WebAssembly
    Dónde correEn el servidor. El HTML se actualiza en el navegador mediante SignalREn el navegador del usuario, con WebAssembly
    InteracciónCada acción va al servidor y vuelve. Ligera latenciaLocal y rápida. Solo llama al servidor por APIs o datos
    Carga inicialRápidaMás larga, porque se baja todo
    EstadoEn el servidorEn el cliente
    Si se corta la conexiónLa aplicación deja de funcionarPuede seguir, si no depende de un backend

    Fuente: diapositivas 5, 7, 8, 11 y 12.

    La presentación lo resume como «Browser + Razor = Blazor» (diapositiva 3). Da cuatro motivos para elegirlo (diapositiva 4).

    • Código reutilizable: el mismo C# se comparte entre el frontend y el backend.
    • Fácil de aprender: si ya conocés C# y .NET, la curva es suave.
    • Rendimiento nativo: con Blazor WebAssembly, el código corre directo en el navegador.
    • Soporte completo para .NET: usa sus librerías y su ecosistema.

    WebAssembly (Wasm) «es un formato de código binario que permite ejecutar código de bajo nivel en navegadores web y otros entornos», con un rendimiento casi nativo. Se diseñó para complementar JavaScript, y permite que lenguajes como C, C++ o Rust se compilen y corran en el navegador de forma eficiente y segura (diapositiva 10).

    Blazor ServerBlazor WebAssembly
    Escenarios idealesAplicaciones que necesitan acceso frecuente a datos del servidor, o que no pueden bajar mucho código al clienteAplicaciones con más interactividad, que pueden correr enteras en el cliente y donde la conectividad no es una limitante constante

    Fuente: diapositivas 8 y 12. La carga inicial de Blazor Server es rápida porque el navegador solo baja un archivo HTML y JavaScript chico para iniciar la conexión con el servidor (diapositiva 7).

    «Se ejecuta en el servidor y utiliza SignalR para comunicar cambios de la UI al navegador del cliente.» Fuente: Presentación de la Unidad 5, Blazor, diapositiva 7.

    Las piezas

    • Componentes: los bloques principales, en C# y Razor (diapositiva 14).
    • Páginas: un tipo especial de componente, asociado a una ruta (diapositiva 15).
    • Rutas: manejan la navegación entre componentes. Van con la directiva @page, admiten parámetros, parámetros opcionales (?) y varias rutas en un solo componente. Al navegar, el navegador no recarga toda la página, porque Blazor actualiza solo la parte necesaria (diapositiva 16).
    • Binding: la sincronización entre la interfaz y los datos. One-way, del código a la vista. Two-way, entre vista y modelo, ideal para formularios (diapositiva 17).
    • Archivos del proyecto inicial: Program.cs, App.razor y MainLayout.razor (diapositiva 18).

    Ventajas: no necesitás JavaScript, se integra con .NET y reutilizás código. Desafíos: el tamaño de descarga y los límites de WebAssembly en el navegador (diapositiva 20).

    Servicios web

    «Los servicios web son componentes de software que permiten que diferentes aplicaciones se comuniquen e interactúen entre sí a través de una red» (Presentación de la Unidad 6, diapositiva 3). Son independientes de la plataforma y del lenguaje, porque otras aplicaciones los usan mediante tecnologías web estándar (diapositiva 3).

    Qué problemas resuelven, según la diapositiva 4:

    • Dan un mecanismo para que las aplicaciones intercambien datos e invoquen funcionalidades de forma remota.
    • Permiten integración e interoperabilidad entre sistemas distintos, sin importar sus tecnologías.
    • Habilitan la computación distribuida. Las aplicaciones aprovechan las capacidades de las demás y comparten datos de forma segura y eficiente.

    La diapositiva 5 muestra cómo evolucionaron, con RPC (1980), DCE (1990), CORBA (1991), COM (1993), DCOM (1996), Java RMI (1997), XML-RPC (1998), SOAP y REST (2000) y .NET Remoting (2002).

    TipoSe apoya en
    Basados en SOAPProtocolo SOAP (Simple Object Access Protocol), XML para el intercambio
    RESTfulPrincipios REST (REpresentational State Transfer), HTTP + JSON o XML

    Fuente: diapositiva 6.

    Los servicios RESTful también se conocen como REST APIs. Son un estilo arquitectónico popular para diseñar servicios web, basado en principios que enfatizan la simplicidad, la escalabilidad y la falta de estado (stateless) (diapositiva 7). La arquitectura pone a los clientes contra una RESTful API, que corre en un servidor web con su base de datos (diapositiva 10).

    Solo en el plan viejo

    Web Forms. Los parciales escritos de 2014 a 2017 preguntan por IsPostBack, Code-Behind, Web.config, manejo de estado, Master Pages, Themes y Skins, y el ciclo de vida de la página. También lo toman las prácticas en capas de 2016 y 2017. El último 2° parcial que leí, del 14/09/2026, no trae nada de eso y pregunta por Blazor. Si tu comisión todavía lo ve, los laboratorios 1 a 6 de la Unidad 5 están en el Drive.

    Lo que dicen las presentaciones de 2015 Aplicaciones Web Parte 1 (P1) y Parte 2 (P2), con el número de diapositiva:

    • Code-Behind. «Diferentes archivos para la gráfica y la lógica», unidos con la directiva @Page (P1, 23).
    • IsPostBack. Page_Load se ejecuta en cada request. Page.IsPostBack sirve para ejecutar lógica condicional y prevenir el reload en cada request (P1, 31).
    • Ciclo de vida. Eventos de página (Page_Init, Page_Load, Page_Unload), eventos de control, de cambio y de acciones, y Dispose, donde se elimina el objeto Page. El orden está en el dibujo de la diapositiva (P1, 29).
    • Manejo de estado. En el servidor, Application (para todos los usuarios), Session (única por usuario mientras dure su sesión) y base de datos. En el cliente, Cookies, ViewState (retiene los valores entre requests a la página) y Query Strings (P1, 34). El lado del cliente es menos seguro y fiable, y guarda menos información (P1, 36).
    • Web.config. «Repositorio central de configuración de la aplicación Web» (P2, 20). Hay uno por aplicación (P1, 18).
    • Master Pages. «Herencia Visual» para páginas web (P2, 5). La master define <asp:ContentPlaceHolder> y las páginas definen <asp:Content> (P2, 7).
    • Themes y Skins. Un Theme es un conjunto de Skins. Un Skin es un conjunto de atributos visuales para uno o más controles, y no reemplaza al CSS (P2, 12).

    MVC. Ninguna hoja de 2023 en adelante lo pregunta. La presentación de la Unidad 6 lo nombra como una de las formas de armar una API. Sale de 3 - Presentación - MVC.ppt, de 2016, con el número de diapositiva:

    • Model. Objetos que implementan la lógica de negocio. Es «totalmente independiente de la View y del Controller» (9 y 10).
    • View. Presenta la UI al usuario. «Practicamente no deberian incluir código no HTML» (9 y 11).
    • Controller. Maneja la interacción con el usuario, consulta al modelo y selecciona la vista adecuada (12).
    • Contra Web Forms. Web Forms representa la página como un árbol de controles con eventos. Su deuda son el Viewstate, el ciclo de vida y el control limitado sobre el HTML (7).
    • Routing. Mapea las URL a controladores y acciones. El enrutado por defecto se define en App_Start/RouteConfig.cs (23).
    • Actions. Métodos del Controller que retornan ActionResult (24).
    • Validación. Con atributos en las propiedades del modelo: Required, StringLength, Range, RegularExpression y Compare (33).
    • Datos a la vista. ViewDataDictionary, ViewBag y vistas fuertemente tipadas (35).
    • Razor. Genera las vistas. El código C# se reconoce por el símbolo @ (40).

    Servicios web con SOAP. Hoy la materia trabaja con API REST. La presentación vieja, Presentación - WebServices.ppt, de 2015, está en la carpeta «Material Viejo» y dice esto, con el número de diapositiva:

    • SOAP. Simple Object Access Protocol, basado en XML y «diseñado para trabajar con objetos remotamente» (11).
    • WSDL. Web Service Description Language, un «contrato que provee definiciones sobre tipos usados en las operaciones» (13).
    • UDDI. Un directorio donde se publican los servicios web de distintas empresas (12).
    • Proxy. Es igual a la clase original pero sin la implementación lógica. Se crea a partir del WSDL y usa SOAP para hablar con el servicio (18).
    • Contra una página web. La página tiene UI e interactúa con usuarios. El servicio no tiene UI e interactúa con aplicaciones (14).
