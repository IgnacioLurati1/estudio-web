La idea general

La materia recorre una sola pregunta: ¿cómo se arma una aplicación real en .NET? Empieza abajo, con lo que pasa cuando compilás. Sigue con el lenguaje y los objetos. Después suma una pantalla, una base de datos, la web y los servicios.

Pensalo como capas de una misma casa. La plataforma es el terreno. C# es el material. Las pantallas, los datos y los servicios son las partes de la casa. Al final del año todo tiene que funcionar junto.

Eso se nota en los exámenes. El 1° parcial en PC te hace armar una solución chica con dos proyectos. La aprobación directa te hace armar una aplicación entera, con pantalla, API y base.

La plataforma .NET

.NET es la base sobre la que corre todo lo que escribís. La cátedra la define así.

«La plataforma .NET es un conjunto de tecnologías diseñado por Microsoft que permiten el desarrollo y ejecución de software, de forma independiente del lenguaje de programación, modelo de objetos, sistema operativo, infraestructura de hardware y dispositivos donde se ejecuta.» (Unidad 1, Capítulo 1, Teoría, pág. 4)

Tiene dos componentes principales.

  • CLR, el motor de ejecución.
  • BCL, la librería de clases.

Se liberó oficialmente en 2002. Hay tres nombres que conviene ubicar.

La presentación da su objetivo y sus beneficios (Presentación de la Unidad 1, Capítulo 1, diapositivas 3 y 4). El objetivo es «ofrecer un modelo de programación potente, flexible y simple (en comparación con lo que hasta ese momento se conocía como COM)». Los beneficios son estos.

  • Interoperabilidad con código existente.
  • Soporte para múltiples lenguajes de programación.
  • Soporte para múltiples sistemas operativos.
  • «Runtime» común compartido por todos los lenguajes y sistemas operativos.
  • Integración entre todos los lenguajes.
  • Extensa librería de clases compartida.
  • Modelo de «deployment» simplificado.
  • Amplio soporte para uso desde línea de comando.

Common Language Runtime (CLR)

«El Common Language Runtime (CLR) maneja el código en tiempo de ejecución y provee una serie de servicios esenciales tales como la integración de lenguajes, seguridad, manejo de tipos seguros, manejo de hilos (thread) y manejo de memoria.» (Unidad 1, Capítulo 1, Teoría, pág. 10)

Es el código que administra a tu código. El apunte lo llama «el verdadero núcleo del framework de .NET». Es el entorno de ejecución donde se cargan las aplicaciones escritas en los distintos lenguajes, y permite integrar proyectos en C#, Visual Basic, C++ o F# (pág. 10). «El CLR es el encargado de gestionar lo que se denomina código administrado», y para eso tiene componentes que dan servicios automáticos al código que se ejecuta (pág. 14).

El CLR también compila. Pasa el CIL a código máquina nativo con una compilación JIT, en tiempo de ejecución y a medida que el programa invoca métodos. El código obtenido queda en la memoria caché y se vuelve a compilar solo si cambia el código fuente (pág. 10).

Compilación: de C# a código nativo

Compilar en .NET son dos pasos. El primero pasa en tu máquina. El segundo, cuando corre el programa.

  1. Elegir un compilador. Cada lenguaje .NET tiene el suyo. El de C# es csc.exe.
  2. Compilar a MSIL. Convierte el código fuente en CIL (o MSIL) y genera los metadatos.
  3. Compilar MSIL a código nativo. En tiempo de ejecución, un compilador JIT (Just-In-Time) convierte el CIL en código nativo. Antes se comprueba la seguridad de tipos.
  4. Ejecutar. El CLR da la infraestructura y sus servicios.

Fuente: Unidad 1, Capítulo 1, Teoría, pág. 11.

El paso 1 se hace a mano solo si compilás por línea de comandos. Con un IDE, ese paso y el siguiente los hace el entorno solo (Teoría, pág. 11, nota 9).

En criollo

El MSIL es como un idioma neutro. Todos los lenguajes .NET se traducen a ese idioma. Después el JIT lo traduce al idioma de la máquina donde está corriendo, a medida que el programa invoca métodos. Por eso el mismo MSIL corre en cualquier arquitectura compatible.

Código en lenguaje intermedio (MSIL)

«El código en Lenguaje Intermedio de Microsoft (MSIL o CIL) es un conjunto de instrucciones independiente de la CPU y sistema operativo, que se puede convertir de forma eficaz en código nativo» (Teoría, pág. 12).

  • Trae instrucciones para cargar, almacenar, inicializar y llamar a métodos de objetos. También para operaciones lógicas y aritméticas, flujo de control, acceso directo a memoria y control de excepciones (pág. 12).
  • Antes de ejecutarse se convierte a código de la CPU con el JIT. El CLR tiene uno o varios compiladores JIT por cada arquitectura compatible (pág. 12).
  • Junto con el MSIL, el compilador genera los metadatos. Describen los tipos del código, sus definiciones, las firmas de sus miembros y los miembros referenciados (págs. 12 y 13).
  • El IL y los metadatos van en un archivo Ejecutable Portable (PE). Gracias a los metadatos, el código es autodescriptivo y no hacen falta bibliotecas de tipos ni IDL (pág. 13).
  • «El MSIL es independiente del lenguaje en el que se desarrolla» (Presentación de la Unidad 1, Capítulo 1, diapositiva 12).

Ensamblados, manifiesto y metadatos

Un ensamblado (assembly) es la unidad básica de un desarrollo .NET. Contiene código IL, una colección de tipos, recursos y un manifiesto. El manifiesto es un conjunto de metadatos que describe su contenido. Se guarda como .exe o .dll (Unidad 1, Capítulo 1, Teoría, págs. 13 y 14).

Los metadatos describen dependencias y versión. Por eso pueden convivir varias versiones de un mismo ensamblado sin conflicto. Para mirar adentro de un ensamblado está ildasm.exe.

El .NET Framework usa el ensamblado como unidad fundamental para la seguridad, la identificación de tipos, el alcance de referencias, el versionado y el despliegue (Teoría, pág. 14). La presentación lo resume así. Son archivos *.dll o *.exe, «unidad mínima de despliegue al CLR», con un número de versión único, que contienen IL y metadata que los describe (Presentación de la Unidad 1, Capítulo 1, diapositiva 13).

CLI, CTS y CLS

Estas tres siglas se confunden. Se ordenan de mayor a menor.

SiglaQué esFuente
CLIEspecificación estandarizada que describe un entorno virtual de ejecución. Está formada por CTS, metadatos y CLSTeoría, pág. 16
CTSEspecifica «cómo se declaran, utilizan y administran los tipos en el motor de ejecución»Teoría, pág. 16
CLSConjunto de características básicas del lenguaje que establece los requisitos de compatibilidad. Sus reglas definen un subconjunto del CTSTeoría, pág. 19

La característica principal del CLI es que las aplicaciones escritas en distintos lenguajes de alto nivel «puedan luego ejecutarse en múltiples plataformas tanto de hardware como de software sin necesidad de reescribir o re-compilar su código fuente» (Teoría, pág. 16).

El CTS cumple estas funciones, entre otras (Teoría, págs. 16 y 17).

  • Da un marco de trabajo para la integración entre lenguajes, la seguridad de tipos y un alto rendimiento.
  • Da un modelo orientado a objetos que admite la implementación completa de muchos lenguajes.
  • Define reglas que deben seguir los lenguajes, para que objetos escritos en lenguajes distintos puedan interactuar.
  • Da una biblioteca con los tipos de datos primitivos, como Boolean, Byte, Char, Int32 y UInt64.

El CLS existe porque, para interactuar con objetos de cualquier lenguaje, un objeto debe exponer solo las características comunes a todos los lenguajes con los que interopera. Todas las reglas del CTS valen también para el CLS, salvo que el CLS defina reglas más estrictas (Teoría, pág. 19).

Base Class Library (BCL)

Es el «conjunto de tipos básicos (clases, interfaces, etc.) que vienen predefinidos en .NET». Están organizados en jerarquías lógicas de nombres, los namespaces. Son independientes del lenguaje (Presentación de la Unidad 1, Capítulo 1, diapositiva 10). La misma diapositiva agrega que es «Extensible y totalmente Orientada a Objetos».

El apunte la describe como un conjunto de soluciones predefinidas y unificadas para las necesidades de la programación, organizado en una jerarquía de clases (Teoría, pág. 20). Trae interfaces, clases abstractas y clases concretas. Las concretas se usan tal cual o se extienden por herencia. Para usar una interfaz, creás una clase que la implemente o derivás de una clase del Framework que ya la implementa (pág. 21).

Namespaces

¿Qué es un Namespace?1° parcial 01/06/2024

«Un namespace se utiliza para declarar un ámbito que permite organizar el código y proporciona una forma de crear tipos globalmente únicos.» Fuente: Unidad 1, Capítulo 1, Teoría, pág. 23.

Puede contener otro namespace, clases, interfaces, structs, enums y delegados. Su acceso es público y no se puede modificar. El principal es System, donde están Int32, Boolean y String, entre otros (Teoría, págs. 23 y 24).

  • Aunque declares un namespace, el compilador agrega uno predeterminado sin nombre, el espacio de nombres global. Está en todos los archivos, y lo que está en él se puede usar desde cualquier namespace declarado (pág. 23).
  • Igual, se recomienda poner siempre el código dentro de un namespace, con la convención CompanyName.TechnologyName (pág. 23).
  • Un mismo namespace se puede definir en dos o más declaraciones. El apunte lo muestra con dos clases, cada una en su bloque namespace MyCompany.ProjectName (pág. 24, y Unidad 2, Capítulo 1, Teoría, pág. 15).

Enumeraciones

Una enumeración es «un tipo por valor que permite definir un conjunto de constantes con nombre». Se declara con enum (Unidad 2, Capítulo 1, Teoría, pág. 16).

  • El primer enumerador vale 0 y cada uno suma 1, salvo que uses inicializadores.
  • El tipo subyacente es int por defecto. Puede ser cualquier entero excepto char.
  • Para pasar a entero hace falta una conversión explícita: int x = (int)Days.Sun;.
  • Suele definirse directo dentro de un namespace.

Fuente: Unidad 2, Capítulo 1, Teoría, págs. 16 y 17.

Son los ejemplos del apunte (Teoría, págs. 16 y 17). Lo que completa el tema:

  • Los tipos admitidos son byte, sbyte, short, ushort, int, uint, long o ulong. Para usar otro que no sea int se escriben dos puntos después del nombre, como en Months: byte (pág. 17).
  • Se define en un namespace para que todas sus clases la usen con la misma facilidad, pero también puede anidarse dentro de una class o un struct. El nombre de un enumerador no puede tener espacios (pág. 16).
  • Todas las enumeraciones son instancias de System.Enum. No se pueden derivar clases nuevas de esa clase, pero sus métodos sirven para comparar, convertir a cadena y convertir desde una cadena (pág. 19).
  • Con el atributo [Flags], los valores se combinan con un OR bit a bit, y Console.WriteLine muestra los nombres combinados (págs. 17 y 18).

Buenas prácticas del apunte (págs. 19 y 20):

  • Si no hay un miembro que valga 0, considerá crear una constante Ninguna. El CLR inicializa la enumeración en cero, y sin esa constante arranca con un valor no válido.
  • Si hay un caso por defecto obvio, usá la constante que vale cero para representarlo.
  • No definas constantes reservadas para uso futuro.
  • Si un método o una propiedad recibe un valor de la enumeración, validalo. Se puede convertir a la enumeración un número que no está definido en ella.

Frente a un tipo numérico, la enumeración deja claro en el código qué valores son válidos, e IntelliSense muestra los valores definidos (pág. 20). La presentación agrega que se la puede pensar como una colección de constantes, y que da una lista de opciones elegibles y autodescriptivas «en reemplazo del uso de banderas» (Presentación de la Unidad 2, Capítulo 1, diapositiva 11).

Excepciones

El apunte arranca por los errores. Algunos se detectan al compilar, como los de sintaxis o semántica. Otros pasan inadvertidos porque son de lógica o necesitan ciertas condiciones para aparecer, como una entrada de datos incorrecta, una división por cero o una falla en la conexión a una fuente de datos (Unidad 2, Capítulo 1, Teoría, pág. 5).

«Una excepción es una alteración del flujo normal de ejecución de una aplicación» (Unidad 2, Capítulo 1, Teoría, pág. 5). Ante una situación no esperada, el .NET Framework lanza una excepción para informar el error, y hay que capturarla y gestionarla (págs. 5 y 6). Las predefinidas derivan de System.Exception y cubren casos como los aritméticos, de formato, de índice fuera del límite de un arreglo o de división por cero (pág. 6). La BCL también tiene System.SystemException y System.ApplicationException (pág. 23).

El motor en tiempo de ejecución controla las excepciones así (pág. 6).

  • Independientemente del lenguaje que las genera o controla.
  • Sin exigir una sintaxis concreta, aunque cada lenguaje puede definir la propia.
  • Permitiendo que se inicien traspasando los límites de los procesos e, incluso, de los equipos.

Frente a otros métodos de notificación, como devolver códigos de error, las excepciones tienen estas ventajas (pág. 6).

  • Ningún error pasa desapercibido.
  • Los valores no válidos no se siguen propagando por el sistema.
  • No es necesario comprobar los códigos devueltos.
  • Es muy sencillo agregar código de control de excepciones para aumentar la confiabilidad del programa.

El orden de los catch importa

Primero los catch de excepciones específicas y después el general, «pues de lo contrario el compilador puede emitir un error» (Unidad 2, Capítulo 1, Teoría, pág. 9).

Qué pasa cuando se lanza una (Unidad 2, Capítulo 1, Teoría, págs. 9 a 11):

  • La excepción asciende por la pila, y cada bloque catch tiene la oportunidad de controlarla. El que la toma se elige haciendo coincidir el tipo de la excepción con el del catch. Si no hay uno específico, la toma el catch general, si existe.
  • Un catch sin tipo detecta cualquier excepción. El apunte recomienda detectar un tipo específico en lugar de usar esa forma básica.
  • Si ningún catch la detecta, la detecta el CLR. Según cómo esté configurado, aparece un cuadro de depuración o el programa se deja de ejecutar y muestra la información de la excepción.
  • Con throw también se vuelve a producir una excepción ya detectada. Es muy recomendable agregarle información, para tener más datos al depurar.

La programación orientada a objetos «es una manera de construir Software basada en el paradigma de orientación a objetos». Propone resolver problemas de la realidad identificando objetos y relaciones de colaboración entre ellos. El objeto y el mensaje son sus elementos fundamentales (diapositiva 3).

Clase y objeto

La clase es «la definición de las características de un determinado tipo de objeto» (diapositiva 24). Implica clasificar en base a comportamiento y atributos comunes. Es una construcción estática que describe el comportamiento común y los atributos (estado), e incluye datos y funciones (métodos) (diapositiva 4).

Un objeto es una instancia de una clase y posee tres cosas (diapositiva 6).

  • Identidad: la relación única entre el objeto del modelo y el ente de la realidad que representa. Se implementa con un id único en el modelo.
  • Comportamiento: resuelve un conjunto particular de problemas.
  • Estado: almacena información, fija o variable.

Los miembros de una clase son los que declara y los que hereda de su clase base directa. Se dividen en constantes, campos (las variables de la clase), métodos, propiedades, eventos (las notificaciones que puede generar), indizadores (indizan las instancias como si fueran matrices), operadores, constructores de instancia, destructores, constructores estáticos (inicializan la propia clase) y tipos (Unidad 2, Capítulo 1, Teoría, pág. 22).

Abstracción y encapsulamiento

La abstracción es «ignorancia selectiva». Decide qué es importante y se enfoca en eso. Ignora lo que no es importante y «utiliza la encapsulación para reforzar la abstracción» (diapositiva 8). El encapsulamiento separa lo accesible desde afuera (métodos públicos) de lo accesible desde adentro (métodos privados). Se usa por control y por cambios (diapositivas 10 y 11).

Un método virtual «es un método que la clase base permite que sea sobrescrito en una clase derivada». En cambio, «un método no-virtual es la UNICA implementación posible para este método» (diapositiva 18).

Qué cambia entre virtual, new y override

public class A
{
    public void F() { Console.WriteLine("A.F"); }
    public virtual void G() { Console.WriteLine("A.G"); }
}
public class B : A
{
    new public void F() { Console.WriteLine("B.F"); }
    public override void G() { Console.WriteLine("B.G"); }
}

El laboratorio hace B b = new B(); A a = b;, llama a F y a G por las dos variables, y te pide analizar la salida. Después pide quitar new: aparece un warning que avisa que, si es intencional, se declare como new. Y pide quitar override: aparece otro warning, y al ejecutar la aplicación llama a A.G().

Interfaces

Una interfaz define un «contrato» (diapositiva 19).

  • Se declara con interface y, por estándar, lleva el prefijo «I» (diapositivas 34 y 35).
  • Sus métodos son implícitamente públicos, sin implementación y sin modificadores de acceso (diapositiva 35).
  • Una clase puede implementar cero, una o más. Una interfaz puede heredar de varias (diapositiva 36).
  • No se pueden crear instancias de ella (diapositiva 19).
  • Contiene solo métodos sin implementación y no hereda atributos. Quien la implementa debe implementar todos sus métodos (diapositivas 19 y 36).
  • Se implementa de forma implícita o explícita. La explícita resuelve conflictos de nombre y solo se accede a través de la interfaz (diapositivas 37 a 41).

LINQ

LINQ integra consultas a C#, desde .NET Framework 3.5 (diapositiva 10). Sus ventajas son una sola sintaxis, detección de errores al compilar, IntelliSense y resultados que se pueden enlazar (diapositiva 13).

La presentación explica para qué nació (diapositivas 9 y 11). Sin LINQ, cada tipo de información se consulta distinto. Una lista con foreach y condiciones, una base con SQL y un XML con XPath o XQuery. La idea es elegir una sola forma de consultar, que el compilador pueda chequear las consultas y los resultados, y que sea extensible a cualquier tipo de datos.

Se escribe de dos formas, que dan lo mismo. Este es el ejemplo de la diapositiva 14.

var contacts =
    from c in customers
    where c.City == "Hove"
    select new { c.Name, c.Phone };

var contacts =
    customers
    .Where(c => c.City == "Hove")
    .Select(c => new { c.Name, c.Phone });

Arquitectura

«Es la descripción de los elementos utilizados para construir sistemas de software, la interacción entre estos elementos, los patrones que guían su composición y las restricciones de esos patrones.» Shaw-Garlan.

Capas lógicas y físicas

  • Lógicas. Estructuran la solución de software y especifican qué componentes van en cada capa.
  • Físicas. Estructuran la infraestructura.

Cada capa se comunica con la siguiente, y cada una se puede cambiar (diapositiva 11). «Los cambios en una capa deberían impactar mínimamente en las demás capas» (diapositiva 12). Lo que se intercambia «son los mensajes del contrato entre dos capas»: DataSets, XML u objetos (diapositiva 15).

El mismo pedido en 1 capa y en 3

Una aplicación de escritorio maneja créditos y débitos de clientes. La solución en 1 capa tiene toda la lógica y el acceso a datos dentro de los formularios. La de 3 capas es una solución con tres proyectos: uno con los formularios, una class library con la lógica y otro con el acceso a datos.

  • Piden también una interfaz web. En 1 capa se vuelve a escribir toda la lógica y todo el acceso a datos. En 3 capas se agrega el sitio web, que hace referencia al proyecto de la lógica, y el acceso a datos no se toca.
  • Piden no permitir débitos ni transferencias con saldo menor a $10. En 1 capa se cambian las funciones en el sitio web y también en la aplicación de escritorio. En 3 capas se cambian solo en la clase de negocio.

Programación asíncrona

Se usa «si tenemos cualquier necesidad I/O-bound», como solicitar datos de una red, acceder a una base de datos o leer archivos. También sirve para código CPU-bound, un cálculo costoso (Presentación de Programación Asíncrona, diapositiva 3).

El laboratorio lo aplica a la API: los flujos asíncronos «son los flujos recomendados para interacciones con una base de datos (I/O-bound)» (Unidad 6, Laboratorio 1, pág. 1).

PiezaQué es
Task y Task<T>Modelan las operaciones asincrónicas
async«Convierte un método en un método asincrónico», y permite usar await en su cuerpo
await«Se suspende el método invocado y se cede el control de vuelta al autor de la invocación hasta que se completa la tarea esperada»
Task.RunInicia trabajo CPU-bound en un subproceso en segundo plano
Task.WhenAllEspera varios trabajos, sin bloquear

Fuente: Presentación de Programación Asíncrona, diapositivas 4, 7 y 8.

El código asincrónico sirve para los dos casos, «pero de forma distinta en cada escenario» (diapositiva 7). La diapositiva 4 marca la diferencia.

  • Código I/O-bound: se espera con await una operación que devuelve Task o Task<T>, dentro de un método async.
  • Código CPU-bound: se espera con await una operación que se inicia en un subproceso en segundo plano con Task.Run.

Los dos casos sin bloquear la pantalla

// I/O-bound: bajar datos de un servicio web al presionar un botón
private readonly HttpClient _httpClient = new HttpClient();
downloadButton.Clicked += async (o, e) =>
{
    var stringData = await _httpClient.GetStringAsync(URL);
    DoSomethingWithData(stringData);
};

// CPU-bound: un cálculo costoso en un subproceso en segundo plano
calculateButton.Clicked += async (o, e) =>
{
    var damageResult = await Task.Run(() => CalculateDamageDone());
    DisplayDamage(damageResult);
};

En los dos casos, mientras se espera, el subproceso de la interfaz queda libre para hacer otro trabajo.

Esperar varios trabajos

public static async Task<IEnumerable<User>> GetUsersAsync(IEnumerable<int> userIds)
{
    var getUserTasks = new List<Task<User>>();
    foreach (int userId in userIds)
    {
        getUserTasks.Add(GetUserAsync(userId));
    }
    return await Task.WhenAll(getUserTasks);
}

Presentación de Programación Asíncrona, diapositiva 8

Reglas de la diapositiva 9:

  • Los métodos async deben tener un await en el cuerpo, o serán ineficientes.
  • Agregá «Async» como sufijo al nombre de los métodos asincrónicos.
  • async void solo se usa para manejadores de eventos.
  • Escribí código menos «stateful». Es decir, no depender del estado de objetos globales (shared state), sino solo de los valores que devuelven los métodos.

Y una que se olvida: await solo puede usarse dentro de un método asincrónico (diapositiva 7).

En criollo

Pensá en pedir un café. Sincrónico es quedarte parado en la barra sin hacer nada hasta que te lo den. Asincrónico es pedirlo, sentarte a contestar mensajes, y que te llamen cuando está. En una pantalla, eso hace que la ventana no se congele mientras espera la base.
